# План кампании PDCA (PLAN, ревизия `r = 1`)

## 1. Классификация: форма, специализированный скилл и стартовый объём (Entry scope)

- **Форма (`form`):** `incremental` (`pdca-incremental`).
- **Специализированный скилл (`overlay`):** `coder` (`pdca-coder`).
- **Обоснование формы (одной строкой):** хотя целевой список из 7 открытых тикетов фиксирован, точный состав каждого следующего шага зависит от знания, получаемого при интеграции нового API `candle-roformer` 1.0.0 (именованные стемы, мультистем-буферы, параметры нормализации/усиления/`invert_spect`) и кодеков аудио-ввода/вывода в общий конвейер и CLI, поэтому результат достигается пошаговыми проверяемыми приращениями без спекулятивной декомпозиции всего бэклога заранее.
- **Стартовый объём (`entry scope`):** при исходном базовом состоянии `0 / 7` выполненных тикетов (установлено входными фактами на снимке `HEAD a1ea0a4`) первый инкремент доставляет первое наблюдаемое положительное приращение (`>= +1` полностью закрытый критерий из глобального набора `AC-1`..`AC-7`, начиная с обновления контракта стемирования/параметров `candle-roformer` 1.0.0 и связанного поведения CLI/конвейера, либо подтверждённый замер базового состояния `0 / 7`, если процедура инициализации кампании требует отдельного шага фиксации baseline) при сохранении глобальных критериев `AC-1`..`AC-7` неизменными на всём протяжении кампании.

## 3. Рецепт измерения для инкрементальной кампании (Measurement method & Incremental recipe)

- **Предикат достижения цели (`goal predicate`):** `satisfied_criteria_count == 7` при отсутствии регрессий по ранее принятым критериям и пользовательским ограничениям (все 7 глобальных критериев `AC-1`..`AC-7` одновременно находятся в состоянии `met`).
- **Метрика и единица измерения (`metric and unit`):** количество полностью выполненных глобальных критериев открытых тикетов из набора `{AC-1, AC-2, AC-3, AC-4, AC-5, AC-6, AC-7}`; единица измерения — целое число закрытых тикетов (`tickets`, целочисленная шкала `0..=7`).
- **Знаменатель и фильтры включения/исключения (`denominator and inclusion/exclusion filters`):**
  - *Знаменатель:* фиксированное множество из `7` глобальных критериев открытых тикетов (`AC-1`..`AC-7`).
  - *Фильтр включения:* тикет засчитывается как `1` тогда и только тогда, когда выполнены все обязательные условия (включая негативные условия, требования к тестам и документации) соответствующего критерия `AC-i`.
  - *Фильтр исключения:* частично реализованные тикеты, изменения без требуемых критерием тестов/документации, а также шаги, нарушающие любой уже принятый критерий или существующую работоспособность проекта, засчитываются как `0` (не дают положительного приращения результата).
- **Условия сопоставимости (`comparability conditions`):** все измерения проводятся на одном и том же рабочем дереве репозитория `/home/alex/sources/karaoke-cli` (относительно снимка `HEAD a1ea0a4` с сохранением незакоммиченных пользовательских правок в `Cargo.toml`, `Cargo.lock`, `README.md`), по одному и тому же неизменному глобальному набору критериев `AC-1`..`AC-7`, в автономном (offline) окружении без сетевых загрузок весов моделей, с требованием монотонности (ранее принятые критерии `AC-i` остаются выполненными на каждом последующем шаге).
- **Базовое значение, минимальный шаг (floor) и целевой порог (`baseline, increment/floor, target`):**
  - *Установленный baseline (из входных фактов `src/main.rs:285-353`, `src/pipeline.rs:69-71,123-172,313-322`, `README.md:36-48,96-119` на `HEAD a1ea0a4`):* `0 / 7` тикетов (пакетная обработка директорий, пользовательские имена выходов, каталог моделей, расширенная диагностика, именованные мультистемы, расширенные аудиоформаты и настройки нормализации/усиления/`invert_spect` отсутствуют).
  - *Минимальный порог приращения шага (`increment floor` / предел обнаружения метода):* `+1` закрытый тикет (`>= 1` новый критерий из `AC-1`..`AC-7` переведён в `met` за шаг изменения при `0` регрессий по уже закрытым критериям; либо подтверждённый `knowledge increment`, если шаг закрывает критическую неопределённость).
  - *Целевой порог кампании (`target`) и его происхождение (`provenance`):* `7 / 7` (`100%` открытых тикетов закрыты); происхождение — прямое требование пользователя («реализации открытых тикетов проекта» — все 7 открытых тикетов).

## 4. Глобальные критерии приёмки (Acceptance criteria — глобальные и неизменные)

Поставленные обязательные критерии воспроизведены без сужения, замены или переформулировки и действуют глобально для всей кампании:

- **AC-1 (#1 — Пакетная обработка директорий):**
  - *Verbatim:* `#1 directory audio discovery, documented recursion/stable order, per-input errors/continue/nonzero summary, overwrite preflight, valid+corrupt test.`
  - *Принимаемый результат и негативное условие:* при передаче директории обнаруживаются поддерживаемые аудиофайлы с документированным поведением рекурсии и детерминированным (стабильным) порядком обхода; ошибка на отдельном входном файле логируется с указанием входа, не прерывает обработку остальных файлов и приводит к ненулевому коду завершения (`!= 0`) с итоговой сводкой; проверка перезаписи (`overwrite preflight`) предотвращает молчаливую порчу/перезапись существующих выходных файлов без разрешения; присутствуют тесты на смешанный набор из валидных и повреждённых входов.

- **AC-2 (#2 — Пользовательские шаблоны/имена выходных файлов):**
  - *Verbatim:* `#2 --custom_output_names JSON partial defaults, reject unknown/path traversal/absolute, vocal sidecars use custom name, tests.`
  - *Принимаемый результат и негативное условие:* флаг `--custom_output_names` принимает JSON с частичным переопределением имён (для неуказанных ключей сохраняются значения по умолчанию); неизвестные ключи стемирования, относительные переходы вверх по дереву (`..` / path traversal) и абсолютные пути отвергаются с явной ошибкой (не создавая файлов вне целевой директории); сопутствующие вокальные sidecar-файлы (субтитры/тексты) именуются согласованно с переопределённым именем вокального выхода; покрыто тестами.

- **AC-3 (#3 — Метаданные и каталог моделей):**
  - *Verbatim:* `#3 metadata catalogue fields name/file/architecture/stems/optional SDR/checksum, list_models/filter/limit/pretty|json, metadata only/no weights downloads, explain obtain, stable JSON/tests.`
  - *Принимаемый результат и негативное условие:* встроенный каталог метаданных моделей содержит поля `name`, `file`, `architecture`, `stems` и опциональные `SDR` и `checksum`; реализован вывод списка моделей (`list_models`) с фильтрацией, лимитом (`limit` > 0) и форматами `pretty` / `json` со стабильной структурой JSON; операции каталога работают исключительно с метаданными и **не** выполняют сетевых запросов или скачивания весов; документация и вывод объясняют, как получить веса моделей; покрыто тестами.

- **AC-4 (#4 — Логирование, диагностика окружения и тайминги стадий):**
  - *Verbatim:* `#4 logging level/debug/timestamp/targets/info default; env_info versions, Candle revision, cuda/metal/device/parallelism/model paths/no secrets/network; path+cause errors; no-weight test; verbose stage timings default output unchanged.`
  - *Принимаемый результат и негативное условие:* логирование поддерживает настройку уровня (по умолчанию `info`), режим отладки (`debug`), временные метки (`timestamp`) и цели (`targets`); диагностика `env_info` выводит версии пакета/зависимостей, ревизию/версию Candle, доступность `cuda`/`metal`, выбранное устройство (`device`), настройки параллелизма и пути поиска моделей **без** утечки секретов и **без** обращения к сети; сообщения об ошибках содержат путь к ресурсу и причину отказа; в подробном режиме выводятся тайминги стадий, при этом стандартный вывод по умолчанию остаётся неизменным; присутствуют тесты, работающие без весов моделей (`no-weight test`).

- **AC-5 (#5 — Именованный набор стемов и мультистем-семантика):**
  - *Verbatim:* `#5 named public stem set retaining convenience, residual vs independent semantics, --single_stem name/per-stem files, four named buffers.`
  - *Принимаемый результат и негативное условие:* публичный API и конвейер поддерживают именованный набор стемов с сохранением удобных методов доступа к `vocals`/`instrumental`, различают семантику остаточного стема (`residual`) и независимых стемов (`independent`), поддерживают выбор любого валидного стема через `--single_stem <name>` и сохранение отдельных файлов по каждому стему, а также работу с четырьмя именованными буферами (`vocals`, `drums`, `bass`, `other`) без потери или смешивания каналов.

- **AC-6 (#6 — Поддержка аудиоформатов ввода/вывода и аудит зависимостей):**
  - *Verbatim:* `#6 FLAC/MP3 read_audio roundtrip duration/sample rate; M4A implemented or documented unsupported; output_format/bitrate/sample_rate clear errors; WAV f32/no silent quantization; dependency audit.`
  - *Принимаемый результат и негативное условие:* чтение аудио (`read_audio`) для FLAC и MP3 сохраняет длительность и частоту дискретизации (проверено roundtrip-тестами); поддержка M4A либо реализована, либо явно документирована и обрабатывается как неподдерживаемая с понятной ошибкой; параметры `output_format`, `bitrate`, `sample_rate` валидируются с понятными сообщениями об ошибках для неподдерживаемых комбинаций (с учётом того, что `candle-roformer` v1 записывает только WAV, либо средства `karaoke-cli` явно документируют/валидируют поддерживаемые форматы); WAV f32 сохраняется без скрытого понижения разрядности (no silent quantization); проведён аудит зависимостей в `Cargo.toml`/`Cargo.lock`.

- **AC-7 (#7 — Нормализация пиков, усиление и инверсия спектрограммы):**
  - *Verbatim:* `#7 input/output peak norm default .9, configurable; amplification default 0/off; invert_spect; exact residual invariant and normalized behavior, tests/flags.`
  - *Принимаемый результат и негативное условие:* входная и выходная пиковая нормализация по умолчанию равна `0.9` и настраивается флагами/конфигурацией; усиление (`amplification`) по умолчанию равно `0` (выключено) и настраивается; поддержан режим `invert_spect`; соблюдается точный инвариант остаточного стема (`residual`) до нормализации и документированное/корректное поведение при включённой нормализации; флаги и инварианты покрыты тестами.

## 7. Минимальное решение и альтернативы (Minimal solution)

- **Выбранный подход:** пошаговая инкрементальная реализация в рамках `pdca-incremental` + `pdca-coder`, где каждый шаг переводит как минимум один глобальный критерий (`AC-1`..`AC-7`) в состояние `met` (начиная с адаптации ядра `pipeline.rs` и CLI под API `candle-roformer` 1.0.0 — именованные стемы `AC-5` и параметры нормализации/усиления/`invert_spect` `AC-7`, затем аудио-ввод/вывод `AC-6`, пакетный обход `AC-1`, пользовательские имена `AC-2`, каталог моделей `AC-3` и диагностика/логирование `AC-4`), с независимой проверкой CHECK и локальным автокоммитом после каждого принятого шага.
- **Отвергнутая альтернатива:** монолитный обычный цикл (`cycle`) на все 7 тикетов сразу — отвергнут, так как при одновременном изменении CLI, аудиокодеков, мультистем-конвейера, каталога и логирования локализация дефектов и проверка инвариантов между шагами размываются, а промежуточные принятые состояния не фиксируются.
